# Phase 5.1 — Feature parity inventory

Originally reviewed 2026-11-09 on `feature/avalonia-migration`, baseline commit `2ba5343` (`feat: add cross-platform Avalonia search prototype`). The Phase 5.1 review was documentation-only. The matrix below is now updated through [Phase 5.3 search/options/report/View implementation](phase5.3-search-options-report-view.md), following [Phase 5.2 settings/history](phase5.2-settings-history.md); the original baseline results and later-step proposals remain labelled as such. No application version, tags or releases were changed.

**WinForms v0.10.0 remains the stable Windows implementation.** Keep its behavior, settings, Windows integrations, tests and publishing path operational. Avalonia is a separate .NET 10 application. UI consolidation is outside steps 5.2–5.6 and requires a later decision after parity. Shared-Core work must preserve the existing WinForms contract.

## Findings and interpretation

The common search pipeline is already reused. Remaining host gaps are exports/save workflow, File/Help actions, dependency UI, native integration/acceptance and viewer interaction refinements. Phase 5.3 adds context/sort/engine controls, captured reports, shared command preview and independent View toggles while retaining Phase 5.2 settings/history/startup policies. Current checks pass: 138 Core and 220 Desktop. The native-menu follow-up also confirms real macOS menu export/fallback hiding; broader native acceptance remains pending. The viewer has working portable formatting, Unicode offsets, selection and incremental rendering, but native interaction and performance acceptance remain outstanding.

The export prerequisite is now present: Desktop captures the existing Core SearchReport with original metadata, raw displayed results, shared spans and final completion status. Phase 5.4 must use that captured report rather than current controls or scraped editor text. ResultsExporter and dependency services remain **internal**. Phase 5.3 additionally exposes SearchReport and the small extracted SearchCommandFormatter; settings API access remains as implemented in Phase 5.2.

Parity labels describe the current **Avalonia application**, not just what Core could do:

- **Complete:** No known implementation gap for this specific behavior in the inspected code, supported by shared implementation and/or existing automated coverage. This does not imply native acceptance on every OS.
- **Partial:** Some behavior exists, but a user-visible difference, host integration gap or material platform integration remains.
- **Missing:** No corresponding Desktop feature is exposed. Existing Core capability is identified separately.

Native acceptance is tracked independently. A headless result is not proof of a native picker, clipboard, default-app launch, OS Quit or human scrolling behavior. Platform equivalents may satisfy functional parity after review; differences must not silently disappear from the matrix.
