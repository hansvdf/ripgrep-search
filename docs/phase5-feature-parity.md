# Phase 5.1 — Feature parity inventory

Reviewed 2026-11-09 on `feature/avalonia-migration`, baseline commit `2ba5343` (`feat: add cross-platform Avalonia search prototype`). The working tree was clean at the start of this review. This document is an inventory and proposal; no functionality, project files, application version, tags or releases were changed. Nothing was committed or pushed during this review.

**WinForms v0.10.0 remains the stable Windows implementation.** Keep its behavior, settings, Windows integrations, tests and publishing path operational. Avalonia is a separate .NET 10 application. UI consolidation is outside steps 5.2–5.6 and requires a later decision after parity. Shared-Core work must preserve the existing WinForms contract.

## Findings and interpretation

The common search pipeline is already reused. Most missing functionality is host wiring: histories/settings, context and sorting controls, engine selection, command preview, menus, export/report capture and dependency-checker UI. The viewer has working portable formatting, Unicode offsets, selection and incremental rendering, but native interaction and performance acceptance remain outstanding.

An important prerequisite for export is absent in Desktop: it retains an AvaloniaEdit document and reduced style/navigation ranges, not the WinForms host's captured SearchReport with original results, presentation spans, search command, start time and completion status. Export must not be reconstructed from current input controls or scraped from editor text. Likewise, settings/export/dependency services already exist in Core but remain **internal**, so simply adding a project reference does not make them available to Desktop.

Parity labels describe the current **Avalonia application**, not just what Core could do:

- **Complete:** No known implementation gap for this specific behavior in the inspected code, supported by shared implementation and/or existing automated coverage. This does not imply native acceptance on every OS.
- **Partial:** Some behavior exists, but a user-visible difference, host integration gap or material platform integration remains.
- **Missing:** No corresponding Desktop feature is exposed. Existing Core capability is identified separately.

Native acceptance is tracked independently. A headless result is not proof of a native picker, clipboard, default-app launch, OS Quit or human scrolling behavior. Platform equivalents may satisfy functional parity after review; differences must not silently disappear from the matrix.

## Proposed implementation steps 5.2–5.6

The boundaries follow the actual dependencies. Settings/history come before persisted options; report capture accompanies search integration rather than being delayed until export; menus are delivered with their owning actions rather than as a disconnected final UI pass. Keep native acceptance checkpoints throughout, with a final consolidated gate in 5.6.

### 5.2 — Settings, histories and host startup policies

**Owns:** S1/S2, H1–H6, startup portion of O1; prerequisite decisions D1–D3.

**Exit evidence:** CT settings contracts remain unchanged; AT restart/history/default/failure/initialization scenarios; native browse/startup smoke tests. Stable WinForms source/behavior/settings untouched. Before shared API work merges, run Windows build/regressions on Windows.
